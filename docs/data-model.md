# Модель данных и Алгоритмы агрегации Staff Pulse

Этот документ содержит математическое описание структуры данных орг-структуры, алгоритмов агрегации показателей по иерархии, а также протокол взаимодействия WebSocket-клиента и сервера.

---

## 1. Иерархическая модель данных

Организационная структура компании представляется в виде ориентированного дерева с одним корнем. В базе данных PostgreSQL и при передаче по HTTP-протоколу используется **плоское представление** (Adjacency List Model). 

Каждый узел содержит ссылку на своего прямого родителя через поле `parent_id` (`parentId` в JSON):

```typescript
interface OrgNode {
  id: string;          // Уникальный строковый ID (первичный ключ)
  name: string;        // Название подразделения
  parentId: string|null; // Ссылка на ID родительского узла (null для корня)
  headcount: number;   // Численность сотрудников данного узла (собственная)
  budget: number;      // Выделенный бюджет данного узла (собственный)
  performance: number; // Собственная эффективность данного узла (0–100%)
  updatedAt: string;   // Дата-время последнего обновления (ISO)
}
```

### Иерархические уровни (глубина):
*   **Уровень 0 (Корень):** Группа компаний (например, `root`). `parentId` равен `null`.
*   **Уровень 1 (Дивизионы):** Крупные бизнес-блоки (например, `div_eng`). `parentId` ссылается на `root`.
*   **Уровень 2 (Отделы):** Функциональные департаменты (например, `dept_backend`). `parentId` ссылается на ID дивизиона.
*   **Уровень 3 (Команды):** Рабочие группы (например, `team_be_core`). `parentId` ссылается на ID отдела.

## 2. Математический алгоритм агрегации показателей

Показатели на вышележащих уровнях (департаменты, дивизионы, корень) должны включать собственные показатели узла, а также **агрегированные показатели всех его потомков** на любую глубину вложенности.

Пусть $Subtree(u)$ — множество, состоящее из самого узла $u$ и всех его потомков (детей, внуков и т.д.) на всех нижележащих уровнях.

### 2.1. Суммарная численность персонала (Total Headcount):
Общее количество сотрудников подразделения рассчитывается как простая сумма численности самого узла и всех его потомков:
$$H_{total}(u) = \sum_{i \in Subtree(u)} headcount_i$$

### 2.2. Суммарный бюджет (Total Budget):
Общий бюджет рассчитывается как арифметическая сумма бюджетов самого узла и всех его потомков:
$$B_{total}(u) = \sum_{i \in Subtree(u)} budget_i$$

### 2.3. Средневзвешенная эффективность (Weighted Average Performance):
Средняя эффективность подразделения рассчитывается как **средневзвешенная величина, где весом выступает headcount каждого узла** в поддереве. Это необходимо для предотвращения математического перекоса, когда маленькая команда с высокой эффективностью необоснованно завышает показатели всего департамента.

Формула расчета:
$$P_{average}(u) = \frac{\sum_{i \in Subtree(u)} (performance_i \times headcount_i)}{H_{total}(u)}$$

*Граничный случай:* Если суммарный штат поддерева равен нулю ($H_{total}(u) = 0$), средневзвешенная эффективность принимается равной собственной эффективности самого узла во избежание деления на ноль:
$$P_{average}(u) = performance_u$$

## 3. Вычисление агрегаций за O(N) через DFS

Для оптимального расчета всех агрегатов за один проход мы используем **пост-фиксный обход дерева в глубину (Post-order DFS)**:

```text
               traverse(node)
                     |
         +-----------+-----------+
         |                       |
         v                       v
   traverse(child_1)       traverse(child_2) ...
         |                       |
   (returns values)        (returns values)
         |                       |
         +-----------> + <-------+
                       |
                       v
             [ Calculate node metrics ]
                       |
                       v
         [ Save node AggregatedMetrics ]
```

### Шаги обхода:
1.  Алгоритм начинает обход с корня.
2.  Прежде чем рассчитать показатели текущего узла, он рекурсивно вызывает `traverse()` для всех его детей.
3.  Дойдя до листьев (команд уровня 3, у которых нет детей), алгоритм сохраняет их показатели (они равны собственным) и возвращает их родительскому отделу.
4.  Отдел собирает данные со всех своих команд, прибавляет к ним свои собственные, рассчитывает свою взвешенную эффективность, сохраняет результат и передает его наверх дивизиону.
5.  Дивизион делает то же самое и передает данные корню.
6.  Сложность алгоритма строго линейна: **$O(N)$**, где $N$ — общее число подразделений. Каждый узел обходится ровно один раз.

## 4. Спецификация контракта WebSocket-патча

WebSocket-сервер бэкенда транслирует изменения в реальном времени. При изменении показателей команды сервер рассылает всем клиентам легкий JSON-патч (структура `WSUpdatePatch`):

### Формат сообщения (JSON):
```json
{
  "id": "team_be_core",
  "headcount": 6,
  "budget": 245000.00,
  "performance": 92,
  "updatedAt": "2026-09-14T19:01:16.145Z"
}
```

### Обработка на клиенте:
При получении сообщения клиент:
1.  Обновляет в кэше React Query поля `headcount`, `budget`, `performance` и `updatedAt` строго для узла с указанным `"id"`.
2.  Кастомный хук `useAggregatedData` (мемоизированный через `useMemo`) видит изменение кэша, заново запускает $O(N)$ расчет агрегации и мгновенно пересчитывает показатели только по цепочке предков вверх, перерисовывая UI.
3.  Никаких повторных сетевых запросов GET не отправляется!
